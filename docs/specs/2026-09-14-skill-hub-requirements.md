# 个人技能中控仓库（Skill Hub）需求文档

- 日期：2026-09-14
- 作者：刘欣（产品专家）
- 状态：已确认（2026-09-14）

## 一、问题与目的

用户在多家 AI 产品（Trae、Codex、Grok、Qoder、Poe/Pi、豆包等）中使用技能，各家的技能目录相互独立。目前靠手工复制与手动开关，存在以下痛点：

- 技能散落在各产品目录，版本容易失控、无法追溯来源
- 没有统一的启用/禁用管理，开关技能要逐个产品去删/加
- 无法方便地从作者仓库更新技能，也无法在更新后保留个人个性化修改

需要一个**个人技能中控仓库**：
- 一个地方集中保管所有技能、来源地址、个性化补丁、启用状态
- 一键把启用的技能推送到所有产品的技能目录
- 上游作者更新时可以跟随，并自动重放用户的个性化修改

## 二、用户与场景

使用者：用户本人（刘欣），单机运行，个人维护。

典型场景：
1. 从某个作者仓库引入一个技能，做登记，再推送到各产品目录
2. 打开网页查看技能列表、切换启用/禁用，同步后产品目录立即生效
3. 上游技能更新了，拉取最新版本，用户打过的补丁自动重放
4. 用 CLI 在脚本/自动化中完成同样的操作

## 三、核心模型（已确认的设计决策）

| 维度 | 结论 |
|---|---|
| 仓库目录 | `c:\dev\skills`（中控仓库） |
| 中控仓库存储 | 按来源仓库分组，保留上游目录树 |
| 上游获取/更新 | 每个来源用 git 子模块/嵌套克隆，保留上游 git 历史；更新 = git pull |
| 元数据 | 集中式清单文件（registry）承载启用状态、来源地址、补丁、目标 |
| 推送布局 | 源分组存储，推送到产品时展平（每个技能自身文件夹落到产品 skills 根下） |
| 启用控制 | 每技能一个全局启用开关；启用的推送到所有产品 |
| 删除语义 | 只管理已登记技能；产品目录里未登记/手动放入的文件一律不碰 |
| 补丁机制 | 集中补丁文件库（`patches/<skill>/xxx.diff`）；上游更新后依序用 git apply 重放，冲突手动处理 |
| 交互 | 本地 Web 与 CLI 并存，共用同一份清单 |

## 四、功能需求

1. **技能登记**：从一个来源仓库（支持本地 git 仓库或可克隆的远程仓库地址）引入技能，保留原目录树，记录来源地址，写入集中清单。
2. **启用/禁用**：通过网页切换技能开关。禁用后源文件保留在中控仓库，但推送时把对应技能从各产品目录中移除。
3. **推送同步**：把「启用的技能」展平后复制到所有目标产品 skills 目录；删除中控仓库中已禁用的技能在各产品目录的副本；不触碰未登记内容。
4. **来源记录**：清单中记录每个技能的上游仓库地址，用于日后追踪和更新。
5. **上游更新**：对某来源执行 git pull 拉取最新版本；变更影响的技能重新推送到各产品目录。
6. **补丁记录与重放**：为某技能添加个性化补丁（diff），存入集中补丁库；上游更新后依序重放，遇冲突给出提示并交由用户手动处理。
7. **网页**：本地 Go 服务，展示技能列表与启用状态，支持开关操作并触发同步。
8. **CLI**：提供 `list / add / enable / disable / push / update / patch` 等命令，供手动与脚本使用。

## 五、约束

- 基于 Go 实现。
- 本地单机运行（Windows 环境）。
- Web 与 CLI 操作同一份清单与同一批仓库目录，需保证一致性。

## 六、成功标准

- 一次操作即可把「当前所有启用的技能」同步到全部目标产品目录，且与清单一致。
- 禁用某技能后，各产品目录中该技能被移除，中控仓库内源文件不丢失。
- 上游更新 + 补丁重放后，产品目录中的技能 = 上游最新版本 + 用户的个性化补丁。

## 七、非目标（YAGNI）

- 不做文件监听自动同步（同步为手动触发）。
- 不做逐产品启用/禁用（全局开关即可）。
- 不做产品目录完整镜像（不清理未登记内容）。
- 不做多用户/多机同步、不做权限与账号体系。

## 八、待定技术决策（交接给 grilling）

以下为「如何实现」层面、留给技术方案设计阶段（grilling）裁决的问题，本需求文档不做技术选型：

1. **清单文件的承载格式**：集中式清单具体用什么格式（YAML/JSON/TOML）？字段如何设计（技能名、来源分组、来源地址、启用状态、补丁引用、所属产品）？仓库根目录到清单文件的路径如何约定？
2. **技能的唯一标识**：技能以什么作为唯一标识（目录名？相对路径？hash？），如何应对不同来源出现同名单技能时的冲突。
3. **来源仓库的引入方式**：git 子模块 vs 嵌套 git 仓库，各自在中控仓库目录树中的位置与布局，.gitmodules / 子目录隔离策略。
4. **推送同步的实现方式**：如何确定「已登记但禁用」从而精准删除目标副本；如何判断同步内容已最新以增量更新；冲突/被本地改动覆盖时的处理策略。
5. **补丁的生成与重放流程**：补丁是手动生成 diff 还是工具对比基线生成；重放顺序、冲突检测与回退策略；补丁与应用的上游版本如何对应绑定。
6. **Web 与 CLI 的关系**：本地 Web 服务的端口与启动方式；Web 是否直接触发文件操作/同步；清单写入的并发与锁。
7. **下游产品差异**：不同产品 skills 目录是否有格式差异（如是否支持嵌套、技能描述文件命名），是否需要针对某产品做适配规则。

## 九、技术方案（grilling 已敲定，2026-09-14）

> 需求文档的「待定技术决策」由上表逐条裁决，结果如下，与需求共同构成完整设计。

### 决策结果
1. **清单格式**：YAML，四分区（targets / sources / skills / patches）。
2. **技能唯一标识**：技能文件夹名；同名冲突时报错，交由用户手动处理。
3. **来源引入方式**：嵌套 git clone 到 `sources/<来源>/`，保留上游 .git 历史；更新 = git pull。
4. **清单字段**：
   - targets（各产品技能目录，支持可选 `subPath`，默认落到 skills 根）
   - sources（git 地址/本地路径、默认分支）
   - skills（id=文件夹名、source、path_in_source、enabled、补丁引用）
   - patches（skill、basestamp=产生时上游 commit、说明）
5. **补丁机制**：在来源嵌套仓库内修改文件（工作区本地改动）→ `patch` 命令用 `git diff 相对基线` 导出到 `patches/<skill>/NNN-描述.diff`，记录 basestamp；`update` 先 fetch 上游、对干净工作区依序 `git apply` 重放，全成功才算完成，失败即停交人工合并并刷新 basestamp。
6. **推送同步**：以 registry 为唯一事实源，先覆盖启用技能（展平到目标），再删除「已登记但禁用」的目标副本；提供 `--dry-run/--verbose` 预览；不碰未登记内容；target 可选 subPath 适配特殊产品。
7. **Web 与 CLI**：单 Go 二进制，`serve` 手动启动本地网页（非守护进程）；CLI 命令复用同一引擎；清单写操作加文件锁。

### 磁盘布局
```
c:\dev\skills\                    # 中控仓库（git 管理）
├── skills.yaml                   # 清单：targets/sources/skills/patches
├── sources/<来源>/               # 每来源一个嵌套 git clone（保留 .git）
│     └── ...上游目录树...
└── patches/<skill>/NNN-描述.diff
```
